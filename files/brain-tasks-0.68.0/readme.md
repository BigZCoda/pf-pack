# skills/brain-tasks/ — the project ledger (tasks and questions per project)

**Created:** 2026-09-04 | **Tool:** `tasks.py` | **Renders in:** the Brain Viewer's Projects panel (`/projects`) | **Decided by:** the owner, 2026-09-04 (ideas A23, open decision 13 in `brain-viewer-holon/brain-viewer-ideas.md`)

## What it is

One ledger file per project, named by the holon registry (a `tasks` field on the holon's row, beside `status`, `rules` and `agent`). The file holds two kinds of item: **tasks** (owned by `@zak`, `@claude`, or a contact) and **questions** (asked by one party of the other). Claude writes tasks for the owner and questions it needs answered; the owner writes tasks for Claude and answers the questions. An agent keeps working on whatever is not blocked; a task blocked on a question is released the moment the question is answered. The same agent picks the answer up when it next reads the ledger, so nothing is re-explained.

The owner asked for this on 2026-09-04: a task list Claude writes to, one project file each, where tasks pass between Claude and the user so the work is collaborative, and questions that need answers show up in the viewer with their files linked and are easy to answer, while the same agent keeps working on whatever it can until a question is answered.

Order of build, his: brain-side first (this), the viewer's UI second (`/projects`), the PF App merge third (a Ferryman-style connector; the app's own project gaps get fixed then, not before).

```
## Inbox
```

- **One item per line.** Segments are separated by ` · ` (space, middle dot, space).
- **Segment 0:** `- [state] ID created-date @owner`, and for questions ` → @to`. IDs are `T-` and four digits for tasks, `Q-` and four digits for questions, counting up from 0001 (the examples in this readme write the digits as `nnn1`, `nnn2` ... so no real ledger's ids appear here), assigned by the tool, unique per file, never reused.
- **Segment 1:** the text.
- **Later segments, any order:** `due:YYYY-MM-DD`, `done:YYYY-MM-DD`, `blocked:<Q id or reason>`, `unblocked:<Q id>`, `until:YYYY-MM-DD` (on hold), `answer:YYYY-MM-DD <the answer>`, `app:<PF App task id>` (once mirrored), `people:<slug>,<slug>`, `note:<one line>`, `repeats:<N>` (times this finding has been raised again), `#tag` — including the two finding tags `#source:<who found it>` and `#key:<the producer's own id for it>`, and `#call:<person-slug>` (raised on that person's next call) — and `→ <link>` (a brain-relative path, a `[[wikilink]]`, or a viewer route like `/glossary`; the viewer opens it in the read drawer, the Reader, or by navigating).
- **`note:` — one line to keep in mind while doing the item** (2026-09-09). Not the reasoning (that lives in the file the `→` link points at) and not a second sentence of task: the single thing to watch. The Brain Viewer's quest log prints it under the item as *keep in mind*. Set it with `--note` on `add` / `ask`, or afterwards with the `note` action (an empty `--note` clears it).
- **The words of an item can be rewritten with `retext`** (2026-09-09). Only segment 1 changes; the id, the created date, the owner, every field and the state are kept, and the rewrite is logged like any other mutation. It exists so a stale sentence never has to be hand-edited into a ledger: the first use was dropping the `(/route)` parenthetical from the eight `#test` items, because the viewer now draws that route as a link beside the item and the parenthetical only repeated it. Give the route as a `--link` when you take it out of the words.
- **The owner of a task can be moved with `reassign`** (2026-09-15). `reassign <id> --owner @claude` rewrites segment 0's owner in place and nothing else: the id, the created date, the state, the due, the note, the people, the tags and the links all stay, so a queue change is one tool call and the line keeps its history. `--reason` says why, and it goes in the `context/log.md` line rather than onto the item. Any `@name` the file already uses is fair (`@zak`, `@claude`, `@replit`, a contact). A **question is refused**: its owner is who asked it and its `→ @to` is who owes the answer, so moving either would rewrite who said what. An unknown id is refused the same way every other verb refuses one. First use was the four tasks that came back off Replit on 9/15.
- **`→ link` on a DONE item is the RESULT — what the item produced** (2026-09-09). A route (`/`, `/glossary`, `/reader?path=<file>`) or a path. The viewer's timeline is nothing but those links read back, so a step closed without one shows as *no result link*. Set it as you close (`done --link`) or afterwards (`link`), and give the result first when an item keeps its source link too.
- **`people:` — who the item concerns** (2026-09-09). Comma-separated `people/` slugs, each validated against a real card on write: no card, no tag. This is the routing. The Brain Viewer's People panel opens a person with **every open question and open `@zak` task that carries them, first, above the card**, answerable there; the counts on the nav, the person rows and the group rows are the same set (`GET /api/badges`). An item with no `people:` field still surfaces if its text names the person or it links their card, but that is a read-time fallback the panel marks as *matched by name* — the field is what routes reliably, and it wins outright when present. Set it with `--people` on `add` / `ask`, or afterwards with the `people` action; `list --people <slug>` filters.
- **`until:` — on hold until that day** (2026-09-10: the owner asked to put tasks on hold for a few days rather than check them off). An open task with a date that has not arrived is **still open and still owed**; it simply leaves the lists that ask for it now — the home's *Waiting on you*, `/projects`, `/people`, the quest log, the nav counts — and comes back on its own on the day. `hold` writes it (three days by default, `--until` for a date, and only on an open task: a question is answered and a blocked task is waiting on someone else), `reopen` clears it, `done` clears it with everything else, and `list` leaves held items out unless `--held` is passed. It is not a state: the mark stays `[ ]`, so nothing that counts open work is fooled. In the viewer it is a **hold** button beside the checkbox with a small date box next to it, and a folded *N on hold* line at the foot of each list.
- **`due:` — the day an item is owed by, and the verb that puts one there** (2026-09-16, the viewer's Today page). The Brain Viewer's **Today** page reads `due:` into *Due today or earlier*, and until now the field could only be written at birth on `add`, so that section had nothing to show for anything already sitting on a ledger. **`today <id>`** puts the clock's own day on an item that exists, **`today <id> --due YYYY-MM-DD`** puts another day on it, and **`today <id> --due none`** takes the day back off. **`ask` accepts `--due`** too, so a question can be owed by a day the way a task is. It works on a task or a question, open or closed, and it never changes state — a day on a done item is a record, not a reopen. `--due` is checked as a real `YYYY-MM-DD` on every verb that takes it now (`add` never checked it, so a typo used to land in the file), and there is still no way to hand the tool a date it calls *today*: the clock is read in the call that writes.
- **`#call:<person-slug>` — the item is raised on that person's NEXT CALL, and the `tag` verb that puts one on an item that already exists** (2026-09-18, the viewer's call preps). The owner asked that what concerns one person's call stay out of the day's tasks and sit inside that call's prep, unless it needs clarifying sooner, for every call. A call-scoped item is still open and still owed — it simply leaves the Brain Viewer's **Today** page, which counts what it left out and says how many are waiting in their preps, and arrives in that person's `## Carried` block instead ([[skills/call-prep/call-prep-format.md]]). The slug is a `people/` card, exactly one person, validated on write the way `people:` is; a group call has no single slug and stays untagged.
  - **`--call <slug>`** on `add` / `ask` writes the tag at birth. The intake and rounds rules now say a "raise it on the next call" item files this way and never as a bare `@zak` task (operational playbook, Step 0.5 and the transcript intake runbook).
  - **`tag <id> --tag <value>`** puts a plain tag on an item that exists, **`--remove`** takes one off, and **`tag <id> --call <slug>`** is the same verb with the slug validated into `call:<slug>`. Until this verb, every tag could only be written at birth, so re-scoping an item meant hand-editing a ledger line — the one thing this tool exists to prevent. Only the tag segment changes: the id, the created date, the owner, the state and every field are carried through the same `rewrite()` every other verb uses. A tag already there (or already absent, with `--remove`) is refused rather than written twice.
  - **`list --call <slug>`** filters, and a bare `--call` returns every call-scoped item whoever the call is with. `--json` carries `call` on every item (the slug, or `null`), which is what the call prep reads.
- **`#source:` and `#key:` — a finding's two tags, and `repeats:` — the count of how often it has come back** (2026-09-17, piece 1 of [[deliverables/findings-routing-design-2026-09-17.md]]). Six things in the brain produce findings — the night agent, brain-lint, the dispatcher, Extended Rounds, holon handoffs, the two inboxes — and none of them wrote to a ledger, so the same finding was raised five nights running with nothing recording that it had been raised before. The rule now: **every finding becomes a ledger item at birth, and a repeat is a note on the open item, never a second item.**
  - **`--source <slug>`** on `add` / `ask` stores `#source:<slug>` — *who* found it: `night-agent-86`, `brain-lint`, `dispatcher`, `handoff`, `extended-rounds-2026-10`. A plain slug: letters, digits, `-`, `_`. A `#` or a space is refused, because both break the tag segment.
  - **`--key <value>`** stores `#key:<value>` — the *producer's own* stable id for the finding, so its next run recognises its own work: `L12:people/a-mentee.md`, `R3:librarian`, `obs41`. Source's rule plus `/`, `:` and `.`. The match key is the producer's to choose and is meant to be **conservative: when in doubt, file a new item** rather than repeat the wrong one.
  - **`repeat <id> --source <slug>`**, or **`repeat --key <value> --source <slug>`** when the producer does not remember ids (a cron, a lint run — it finds the one *open* item carrying that key across every registered ledger). It bumps `repeats:N` and **appends** a dated line to the item's `note:` — `repeat 2 (night-agent-86, 2026-09-17): still there` with `--text`, after ` | ` — so the history of a standing finding reads in order on the item itself. `note` still *replaces* its line (it is one thing to keep in mind); only `repeat` appends. `--text` is optional. Exit **3** = no open item with that key, so file a new one; exit **4** = more than one, and it lists the ids.
  - **`list --source <prefix>`** (a prefix, so `--source night-agent` catches every run) and **`list --key <value>`** (exact) filter, and unlike the older filters they also narrow `--json`, which is what a producer checking "is this already filed?" needs. Every item in `--json` carries `source`, `key` and `repeats` at top level, so the viewer's Findings view never re-parses tags.
  - **`route <path>`** answers *which ledger* a finding belongs on: the holon in `context/holon-registry.json` whose `path` is the longest prefix of the file the finding names, `brain-central` when nothing matches. It prints `<holon-id>\t<ledger file>` (`--json` for the object), writes nothing and logs nothing. It exists so the six producers do not each reimplement the same mapping.
- **States:** `[ ]` open · `[x]` done · `[-]` blocked · `[?]` question open · `[a]` question answered.
- **Groups:** `## Milestone — <name>` headings. Items before any heading, or under `## Inbox`, are the inbox. The word is *milestone*, not *quest*: the brain's earlier quest concept is a different thing and stays separate until the owner coordinates them (ideas A24).
- **Dates come from the clock** when the tool writes. The only flags that accept one are `--due` and `--until`, and both are checked as real dates before the line is written. Hand edits are welcome in the same shape; `tasks.py check` catches a line that no longer parses.

```
python skills/brain-tasks/tasks.py tag    --project pf-build T-nnn6 --call a-mentee                                                                  # ...or put the call tag on an item that already exists

python skills/brain-tasks/tasks.py hold   --project brain-viewer-holon T-nn10 --until 2026-09-20                    # ...or until a day you pick
```

`--file <brain-relative path>` bypasses the registry. `--agent <id>` names the writer in `context/log.md` (default `brain-tasks`; the viewer passes `brain-viewer`). Every mutating call logs one `MODIFIED` line through `skills/brain-log/log.py`.

## How agents use it

- 🔴 **Since 2026-09-08 the ledgers are the ONLY home of open items for the owner; the state files point.** `context/current-focus.md` and `context/claude-task-queue.md` carry pointers and history, never live open boxes — an open box found in either is a migration miss, so move it here rather than re-asking it in chat. Rounds Step 0a reads the ledgers first.
- **A holon session boots** by reading its project's ledger (open tasks for `@claude`, open questions it asked, answers that arrived). The ledger is now the third item in the holon readme's boot list.
- **At a handoff**, the "NEEDS FROM YOU" lines become `@zak` tasks or questions, and the not-done list becomes `@claude` tasks. The handoff file stays the narrative; the ledger is the state.
- **When blocked**, `ask` the question, `block` the task by it, keep working on the rest. Do not restate the question in chat every turn; it is in the viewer.
- **Never** write the file by hand from an agent. Use the tool, so the date is the clock's and the log line exists.
- 🔴 **`--text` and `--note` never carry transcript line references** (2026-09-25): no `L612`, no `(L591 to L603)`. Put the evidence in `--link` to the transcript or the subject file. The owner asked for this that morning after line codes reached every page he reads; his words are in the corrections log, not here. `add`, `ask`, `note`, `retext`, `answer` and `repeat` print a WARN to stderr when one gets through (outside a `<!-- -->` comment); the write still happens.
- 🔴 **Every item is written for a person opening the card cold, days later** (2026-10-02, correction 98 in [[zak-corrections-log.md]], where the owner's words on the card that caused it are kept). The failure it fixes: a card that said "correction #93" and a bare item id, which no reader could follow. Four rules, all on `--text`:
  1. **A question says in its first sentence, in plain words, what is being asked.** Background comes after.
  2. **Nothing referenced is left bare.** A correction number, an item id, a finding name, an internal key: each is written out in a clause saying what it is, and the file that holds it goes in `--link`. A bare `#93`, `T-nnnn` or `Q-nnnn` never stands as the explanation of anything. The forms `check` accepts: *the described thing (pf-build T-nnnn)*, *T-nnnn (three or more words of meaning)*, *correction 87 (what it says)* with `zak-corrections-log.md` linked.
  3. **`#source:` and `#key:` are fields, never meaning.** They tell an agent who filed it; they tell the reader nothing.
  4. **No time estimate** (*Effort: an hour*, *half a day*) unless it is quoted from a thing that ran.
  - **Before** (a question on the central ledger, 10/02): *"Over-elaboration outside the creative-brief scope of correction #93 happened again (the night agent's 9/23 finding, brain-central T-nnnn). Promote it to a correction of its own, or leave it as an observation?"*
  - **After** (the same question, re-posed): *"Should a short answer to a plain question become its own correction, yes or no? On 9/23 a plain re-explanation the owner asked for ran about 700 words. The one correction on over-length today, correction 93 (on a creative brief, build from what he already has and stop adding when he says it is too much), covers design briefs only, so it does not reach a plain explanation. The night agent's 9/23 finding is linked."* The first sentence is the question; every reference carries its meaning and a link; nothing quotes the owner.
  - **The tool helps, it does not refuse.** `add`, `ask` and `retext` print a WARN when the text carries a bare reference or a time estimate, and `check` prints a `COLD` line per ledger counting the open items addressed to `@zak` that break the rule (`check --verbose` names why). The heuristic is deliberately rough; a clean `check` is the floor, not the bar.
- 🔴 **A note never repairs a stale text; when an item's premise has changed, `retext` it** (2026-10-05). The 10/05 task review found a mentee's form task still telling the owner to keep the mentee on the register if a mentor's group did not work out, three days after the mentee had been accepted, and wrote the change as a `note` under the old words. The owner read the words, not the note, and had to restate a fact he had already given (the record is the corrections log, its 2026-10-05 entry). The text is what he reads first on every card; a note is a second layer. When the facts an item rests on have moved (a person placed or not, a date set, a plan replaced), rewrite the text to the current state with `retext`, and keep the note for what to keep in mind while doing it.
- 🔴 **The pose gate: a question the owner cannot answer as written is refused, not warned about** (2026-10-05). A question that asked the owner to choose among Claude's filing categories and named the night agent's weight scale could not be answered as written, and he asked that no question reach him in that shape again; a warning had not stopped it (the record is the corrections log, its 2026-10-05 entry). `ask --to @zak` and `retext` on a question to him now exit with the reason when the text (1) does not put the question in its first sentence (no `?` and no "yes or no" in the first 260 characters, unless it opens with an instruction such as Accept, Confirm, Approve, Rate), (2) asks him to choose among Claude's filing categories (become a correction or a rule, or be archived; promote it; archive the observation): that choice is Claude's own (correction 96), and a rule that needs his acceptance is stated as the rule itself, `Accept this as a standing rule, yes or no: <rule>.`, (3) names Claude's machinery (the night agent, run numbers, weights, obs numbers, lint, the dispatcher, the librarian, the hot cache, state files, findings, repeats, memory rules, `#source` / `#key`): say what happened, not which agent or file noticed it, or (4) comes from an automated `--source` (night-agent, brain-lint, dispatcher, librarian, scout, brain-close): those file a task Claude owns, text beginning `Pose to the owner: `, and the morning session poses it. `check` prints a `POSED` line per ledger and **fails** on it, so brain-lint at rounds catches a question that got in around the gate. Only what only he decides reaches him at all (corrections 96, 77, 74): anything derivable, any default that will do, and anything about how Claude files its own records is decided by Claude and recorded with `answer --by @claude`.
- 🔴 **A question that offers choices names them with `--options`** (2026-10-05). The Brain Viewer answers a question with one press per choice, and without this field it guesses the choices from the sentence: a three-way question that opened with "Should" was drawn as Yes / No on the owner's Today page. `ask --options "a correction | a rule | archive"` stores `options:` on the line, two to six short phrases with `|` between them; `options <id> --options "..."` sets or clears it on a question that exists; `ask` prints a WARN when the question sentence has an "or" and no options were named. A plain yes-or-no question needs none. The viewer still reads an "Options: a, b." sentence or a bare "Accept, reword, or strike." after the question, so older items keep working; the field is what makes the presses certain.
- 🔴 **A question about a person carries `--people`.** The owner asked on 2026-09-09 that every question go to the specific place it belongs. If an item is about somebody with a card, tag it when you write it — that is what puts it on their page in the viewer, where he answers it. Several people is normal (`--people a-mentor,a-teammate`); a person with no card is not taggable, so add the card first or leave the field off. Do not tag a person merely mentioned in passing: the field means *this item is about them*.
- **A document that holds decisions for the owner is linked, section by section, from the ledger.** The owner asked on 2026-09-09 that the agent link those documents and ask, through the Projects panel, for the portions that need attention. When a build doc, a spec, a handoff or an audit carries something he must strike, reorder or decide, the agent asks on the right ledger with `--link <file>#<heading>` pointing at that section (deep links into a document are the Doc module's job, step 2b of the straight line; until it lands the link opens the file). The Projects panel is where he sees the portion that needs him; the document stays whole. The same hover glossary that underlines terms elsewhere runs inside those sections.
- **Close a step with `--link` to what it built; the timeline reads it.** The Brain Viewer's quest log (top right of every page) shows the **timeline** of everything done, newest first, where each entry links to what that item produced. So a step that closes without a result link is a gap in the record of the build: `done --link /glossary`, or `link` afterwards. 🔴 **A closed step records how to try it on the what's-new page** (`brain-viewer-holon/brain-viewer-whats-new.md`: what to open and what to press), **never as a task in the owner's name** (2026-10-06, the owner's yes on the viewer review: 38 of his 40 viewer items were click-through tests filed by the rule that stood here until then, every closed step adding its own `#test` items for him). The `#test` tasks that rule left open stay open and unclosed: the viewer keeps them off Today and the home board and shows them under *To try* on the rating page (`/review`).
- **If answering needs him to look at an image, link the image on the item.** The owner asked on 2026-09-08 that any item needing an image to be viewed link that image. The `→` link goes to the picture he must judge (a preview of the options, not the raw source), filed inside the brain so the viewer opens it in the lightbox. Same for a handoff line or a chat question: the image travels with the ask, never "see the file I sent earlier."
- 🔴 **A finding carries `--source`, and it is `repeat`ed rather than filed twice** (2026-09-17). Any agent that finds something — an audit line, a lint check, a dispatcher suggestion, a handoff's *for the central agent* block — files it on the ledger `route <the file it names>` returns, with `--source <who found it>`, `--key <its own id for it>` and `--link <the evidence>`. Before filing it looks for its own open item (`list --key <value> --json`); a hit becomes `repeat`, never a second item. The audit file, the lint output and the dispatcher report still exist — they are the evidence — but the ledger is the state, and rounds triages what is on it.

## What it is not

Not the brain's old per-session task queue (`context/claude-task-queue.md`, retired 2026-09-17 — these ledgers replaced it). Not the PF App's tasks (the app merge is step three; `app:<id>` is where the mirror will hang). Not a place for prose: a task is one line; the reasoning lives in the file the `→` link points at.

## Registering a project

Add `"tasks": "<folder>/<name>-tasks.md"` to the holon's row in `context/holon-registry.json`, then `tasks.py init --project <id> --name "<Name>"`. The viewer's Projects panel lists every holon with a `tasks` field. A `tasks` field is also what makes a holon a **routing target**: `tasks.py route <path>` only ever returns a holon that has one.
